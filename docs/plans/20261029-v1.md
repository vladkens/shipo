# shipo v1: the updater out of nimbo, the packer in Rust

The goal: everything nimbo does today for releases and updates works the same from shipo, with nothing of it left needed in nimbo. Wavo is the first app (vladkens/wavo-app). Agreed with the person on 2026-10-29.

## What we start from

All of it works today in vladkens/nimbo at `main` (5d08f06) and is proven in CI and in the VMs: a notarized DMG, the NSIS setup installing and updating v1→v2 silently on Windows 11, the AppImage and .deb on Ubuntu (wavo-app run 40936282785).

- The updater: `src/update.rs` (its module docs are the current contract, with the install table per OS), `src/platform/{macos,windows,linux}/app/update.rs`, `…/app/http.rs` (NSURLSession, WinHTTP, libcurl loaded at run time; http is used by nothing else in nimbo), and what they use: `src/platform/*/app/process.rs` (`alive`, `detach`, `wait_exit`, `closed`), `src/platform/linux/dl.rs`, `src/uninstall.rs` (`remove`, `retry`, `app_of`, `app_path`, `Env`), `src/paths.rs` (`OS`, `Os`). `examples/update.rs` and the tests in `src/update.rs`.
- The packer: `scripts/pack.py` (1,682 lines, Python stdlib): the config from `[package.metadata.nimbo]` through `cargo metadata --no-deps`; PNG decode and encode, resize and crop, `.icns`, `.ico`; the Mach-O `minos` reader; `app` (Info.plist, signing); the `.DS_Store` writer; `dmg` through `mkfs.hfsplus` and libdmg-hfsplus; rcodesign for signing, notarizing and stapling; the NSIS script; the PE resources (icon, VERSIONINFO, manifest); AppImage through appimagetool; .deb through `dpkg-deb`; `feed` and `feed-key` through OpenSSL; the commands `app`, `release`, `feed`, `feed-key`.
- How an app uses them: wavo-app's `Makefile` (`dist`, `pack`) and `.github/workflows/`, and vladkens/actions `rust-publish` (its `pack:` input runs the app's `make pack` on `ubuntu-latest` with the secrets APPLE_CERTIFICATE, APPLE_CERTIFICATE_PASSWORD, APPLE_API_KEY, APPLE_API_KEY_ID, APPLE_API_ISSUER, UPDATE_KEY).

## Decisions

- One repo, a Cargo workspace: the root crate `shipo` is the library (the updater), `cli/` is `shipo-cli` with the binary `shipo` (the packer). An app depends only on `shipo`; it never builds the packer's dependencies.
- The library has no UI and no state: `check` gives the release (with the new notes link), `download` and `install` do the work, `finish` runs first in `main`. The menu item, the popup, the "check daily" setting, the check time and a skipped version are the app's; for apps on nimbo, nimbo's `update::dialog` (nimbo #55, merged 2026-10-30) draws the window and keeps its state.
- The packer is Rust. Its own code replaces only the DMG toolchain (the GPL libdmg-hfsplus built in vladkens/actions' tools release, and `hfsprogs`); the rest stays external for v1:
  - rcodesign 0.29.0, fetched pinned by sha256 as pack.py does: signing the app and the DMG, notarizing, stapling. On a Mac, `app` signs with `codesign` as today.
  - From apt, required on the host: `makensis` (nsis), `dpkg-deb`, `mksquashfs` (squashfs-tools), `openssl` (only for the .p12 to PEM step rcodesign needs).
  - The AppImage needs no appimagetool: it is the type2 runtime (pinned by sha256 as in pack.py) with a squashfs from `mksquashfs -comp zstd -root-owned -noappend -b 128K -mkfs-time 0` appended, as appimagetool makes it (`appimagetool.c`) and Velopack does (`AppImageTool.cs`).
  - The feed is signed in process (`ed25519-compact`, shared with the library); OpenSSL is not needed for it.
- The DMG is our own writer: an HFS+ volume (TN1150) holding the `.app`, the `/Applications` symlink and the `.DS_Store`, in a UDIF image compressed with zlib (UDZO, as `hdiutil` makes; `flate2`), not LZMA. The same writer runs on a Mac, so the packer uses no `hdiutil`.
- Packer dependencies, each for code that would be large of our own: `toml` (the config), `png` (any PNG read), `lexopt` (the arguments), `ed25519-compact` (the feed's signature and the keys), `flate2` (zlib for the DMG; `png` brings it already), `hmac-sha256` (the pinned tools' SHA-256; no dependencies). The tools are fetched by the system's `curl` and `tar`.
- The config is read from the app's `Cargo.toml` by `toml`, not `cargo metadata`, so the same reader serves a `shipo.toml` later: `version`, `authors` and `repository` with `workspace = true` from the root's `[workspace.package]`; the binary is the one of `[[bin]]`, `src/main.rs` and `src/bin/*.rs`, else `default-run`, else the package's name; the target folder `CARGO_TARGET_DIR`, else `<workspace root>/target`.
- The config table is `[package.metadata.shipo]`, the same keys as `[package.metadata.nimbo]` today. A `shipo.toml` for apps not in Rust comes later.
- Names change from nimbo's: `--shipo-install` for the installer's argument, `.shipo-update-*` for the staging folders, `SHIPO_UPDATE_ERROR` for the note; the NSIS uninstaller removes `.shipo-update-*`.
- New in the contract:
  - `Feed` takes a list of public keys; a feed signed by any of them is accepted. `keygen` makes the working key and the spare together (the working one for the repo's secret, the spare kept offline, never in CI); both public keys go into the app.
  - A `notes <url>` line in the feed, the release page `<repository>/releases/tag/<tag>`, written by the packer, covered by the signature, and in `Release` as `notes`. Old clients skip a line of an unknown first word.
- The packer is released as prebuilt static binaries (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `aarch64-apple-darwin`) on shipo's GitHub releases. An app's release job downloads one pinned by version and sha256; it never runs `cargo install`, so no crate's source reaches the job with the secrets.
- Agreed 2026-10-30, for the packer:
  - It knows nothing of nimbo: an app's runtime libraries go in its own `linux.deb-recommends` (wavo lists GTK 3 and the rest); the uninstaller still removes launch at login by the app's id, and the `.desktop` keeps `StartupWMClass=<id>`.
  - Nothing tied to GitHub but `release`'s URLs: `keygen [<file>...]` writes a key per file, by default `update.key` and `update-spare.key` (the seed in hex, 0600, never over a file there), and prints each public key, `keygen --public <file>` a key's public half (pack.py's `feed-key` and `feed --public-key` go); the app may hold any number of keys, two the rule; `feed` and `release` take the key from `--key <file>`, else `SHIPO_UPDATE_KEY` (one name, ours; a job maps its secret onto it); `feed --url <base>` (`{version}` the version) and `--notes <url>` serve any host. readme.md documents it, with the steps to replace a key.
- Out of v1: a C ABI, feed lines for an expiry and the app's id, Authenticode, channels, staged rollout, deltas, an MSI; rewriting rcodesign, NSIS, squashfs or the .deb.

## Tasks

- [x] 1. `spec.md`, the contract, from `src/update.rs`'s docs and pack.py, with the changes above: the feed (records, platforms `<os>-<arch>`, size, SHA-512, URL, `notes`, the signature line, a list of keys, unknown lines skipped, the 1 MiB limit); the release file names (`<Name>-<tag>-<platform>.<ext>`, the dev label); where the app is installed and how it is replaced on each OS (the table in `src/update.rs`); the handshake between the app and the installer (`--shipo-install`, the staging folder, `SHIPO_UPDATE_ERROR`); the per-user setup's registry keys, folder and `/S`; the key-leak runbook (sign with the spare, the same release drops the leaked key and carries a new spare).
- [x] 2. The library: move the updater and its platform code from nimbo into `src/`, with copies of the small helpers it uses (process, dl, the remove and retry helpers, the app path rules), the renames and the two contract changes. Port its tests and `examples/update.rs` (a console app, no UI). `make check` and `make test` on macOS, plus clippy for `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`. Report the crate count.
- [x] 3. The packer, all but the DMG: port pack.py command by command into `cli/` (`app`, `release`, `feed`, `keygen`), with the decisions above. pack.py is where the logic comes from, not a reference to match byte for byte: each format is checked by unit tests and by the system's own reader (agents.md).
  - [x] Config: `Cargo.toml` through `toml`, `[package.metadata.shipo]`, the workspace's inheritance, the binary and the target folder; the arguments through `lexopt`.
  - [x] Images: PNG read and write, resize and crop; the `.icns` and the `.ico`.
  - [x] `feed` and `keygen`.
  - [x] `app`: the Info.plist, the Mach-O `minos`, `codesign` on a Mac, rcodesign elsewhere; the `.DS_Store`.
  - [x] Windows: the `.nsi`, the PE resources, `makensis`.
  - [x] Linux: the `.desktop`, the AppImage (the runtime and `mksquashfs`), the `.deb`.
  - [x] `release`: the files per triple and the feed, the whole run in an Ubuntu container.
  - [x] readme.md: the commands.
- [ ] 3b. The packer on any host, with nothing to install (researched 2026-10-30: each tool's own code is small, no crate needed): rcodesign takes the `.p12` itself (`--p12-file`, a password file; a `.p12` it can't read asks for a `-legacy` export), so no `openssl`; the `.deb` our own (`ar`, ustar, gzip by `flate2`); the AppImage's squashfs our own (gzip blocks, which the type2 runtime reads; zstd later if the size matters); tar and zip read by our own code, `curl` kept (macOS, Windows 10+ and Ubuntu have it). Packages are built as trees in memory, modes and links set by the writer, so nothing is staged on disk. `release --key` without `--tag` is an error. Formats are written from their specs (deb(5), the squashfs format docs), never from GPL sources. Checked by the same system readers as before. The packer's hosts are Linux (x86_64, aarch64) and macOS on Apple silicon (agreed 2026-10-30); Windows as a host, with a setup of our own instead of NSIS (a Rust stub, as Velopack's) and a zip reader for rcodesign's Windows build, waits until someone asks.
- [x] 4. The DMG writer: HFS+ and UDIF UDZO in `cli/`, the layout as today (the app at (160,170), Applications at (480,170), a 640×400 window, 128 px icons); the `.DS_Store`'s names in the normalization the HFS+ writer stores (NFD), tested with a non-ASCII app name. Checked on a Mac: `hdiutil verify`, `hdiutil attach -readonly`, `fsck_hfs -n` on the device, the files, modes and the symlink as on the stage; on Linux `fsck.hfsplus -n` (hfsprogs, for tests only). Then signed (ad hoc, and by rcodesign with a throwaway certificate) and checked by `codesign --verify`; `spctl` and the Finder shot need a Developer ID and the VM, so they are task 6's.
- [ ] 5. CI for shipo (`.github/workflows/`, `ubuntu-latest`, `macos-latest`, `windows-latest`): `make check`, `make test`; on Ubuntu with nsis, squashfs-tools and desktop-file-utils from apt, also the packer's ignored tests (`cargo test -p shipo-cli -- --include-ignored`: the real setup, .deb and AppImage, rcodesign); and an end-to-end test: build a test app at v1 and v2, pack both on Ubuntu, then on each OS install v1 and update it from v2's feed served from the runner, silently, and check the version that runs. Releases of the packer binaries through vladkens/actions (`rust-build`, `rust-publish`).
- [ ] 6. The proof with the real secrets: a wavo-app branch packs a release with shipo instead of pack.py (the person runs it, or adds the secrets to shipo); the DMG is notarized and stapled (`xcrun stapler validate`, `spctl -a -t open --context context:primary-signature`, a quarantined first launch in the macOS VM, a Finder shot of the mounted window read and compared with today's DMG), the setup installs and updates on Windows 11 in the VM, the AppImage and .deb run on Ubuntu.

After v1, in other repos and PRs: wavo-app moves onto shipo; nimbo drops `src/update.rs`, its platform code and `scripts/pack.py` (its `Png` and launcher stay); its `update::dialog` stays, over a small release type of its own (version, notes link), which the app fills from `shipo::Release`, so nimbo never depends on shipo.
